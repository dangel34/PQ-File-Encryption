# pqfile Roadmap

This document tracks planned improvements, new features, and security work across future releases. Breaking changes to the `.pqf` format or public API always require a major version bump.

---

## v4.0.0 through v4.3.0 (complete)

All features from v2.x through v4.3.0 are complete. A full history is available in `docs/CHANGELOG.md`. The highlights:

- ML-KEM (512 / 768 / 1024) and hybrid X25519+ML-KEM-768 key encapsulation (FIPS 203)
- ML-DSA-65 digital signatures and signcrypt (FIPS 204)
- Multi-recipient encryption, Shamir M-of-N threshold key splitting, key revocation
- v8 anonymous recipient format (uniform slot size, no per-slot variant field)
- v9 padded-recipient format (slot count rounded to next power of two with random dummy slots)
- Hardware-backed private keys via OS credential store (Windows, macOS, Linux)
- Streaming AEAD with chunk authentication, parallel processing, zstd compression
- `PqfWriter<W: Write>` streaming encryptor, `PqfReader<R: Read>` streaming decryptor
- `AsyncPqfWriter` and async decrypt backed by Tokio (`pqfile` feature `"async"`)
- `encrypt_stream_pipelined` (I/O and AEAD overlap), `encrypt_mmap` (zero-copy mmap)
- Adaptive chunk sizing: auto-tunes to 16 KiB / 64 KiB / 256 KiB based on file size
- Atomic output writes: all CLI file writes use temp-file-then-rename with directory fsync on Unix
- Structured JSON error codes (`docs/ERROR_CODES.md`)
- `pqfile doctor` diagnostic subcommand for key and ciphertext health checks
- Cross-version compatibility matrix in `pqfile/tests/compat/` covering v2-v9
- Property-based tests (`proptest`) and mutation testing CI (`cargo-mutants`)
- Branchless GF(256) arithmetic in Shamir: constant-time `gf_mul` and `gf_inv` via fixed 7-squaring chain
- Key commitment in chunk-0 AAD: SHA3-256(session_key) bound into first AEAD tag
- `PqfileError::Truncated`: distinguishes clean truncation from authentication failure
- Header validation: `original_size` capped at 1 TiB, recipient count capped at 256
- Encrypted archive format (PQFA), rekey, add-recipient, secure file shredding
- Native GUI (egui), CLI, and WASM web app sharing one core library
- Typed key API, `inspect_stream`, formal stability promise in `STABILITY.md`
- Security hardening pass (v4.1.1): timing oracle closed, signdecrypt stdout buffered, Shamir coefficients zeroized, decompression bomb protection, PqfWriter debug-mode drop panic
- GUI: watchfolder, key expiry/renewal, drag-and-drop, recent files, QR codes, clipboard encrypt/decrypt, SSH key import, passphrase strength meter, segmented sub-tabs, scroll indicators
- `passphrase_strength` promoted to public `pqfile::keygen` API; CLI warns on weak passphrases at keygen
- `#[must_use]` on `PqfWriter::finish` and `AsyncPqfWriter::finish`
- Published to crates.io as `pqfile`; supply-chain audited via `cargo vet` and `cargo deny`
- `PqfileError::NoMatchingRecipient` extended with `slots_tried: usize` field for diagnostic context
- `MultiEncryptBuilder` fluent API wrapping all three multi-recipient formats (v4/v8/v9); `.with_progress(cb)` for progress callbacks
- `encrypt_stream_with_progress`, `encrypt_stream_multi_anon_with_progress`, `encrypt_stream_multi_anon_padded_with_progress`, and `decrypt_stream_with_progress` for progress tracking
- Background thread for encrypt/decrypt on desktop (already present since v4.0); per-file byte progress bar wired into desktop GUI
- `PqfileError` source chaining: `Io(#[from] std::io::Error)` already exposes the root via thiserror's `#[from]` (implies `#[source]`); no other wrapping variants hold actual error sources
- WASM CI smoke test: `pqfile/tests/wasm_smoke.rs` with 4 `#[wasm_bindgen_test]` cases; `wasm-test` job added to ci.yml runs via `wasm-pack test --node`
- Chunk boundary property tests at 16 KiB, 64 KiB, 256 KiB tier edges (off-by-one coverage)
- CLI integration tests: truncated ciphertext and bit-flipped ciphertext both correctly rejected
- `--threads N` global CLI flag caps Rayon worker threads for `--parallel` operations; default 0 uses all cores
- Security hardening pass: bounded the previously-unbounded reads in v2 and `async`-feature decrypt/encrypt; private key and Shamir share files now written with 0600 permissions on Unix; Shamir `split_raw` shares zeroized; GUI passphrase clones re-wrapped in `Zeroizing` before use; hardware credential store moved to byte-native secret storage with transparent legacy-format migration; v9 recipient shuffle retry loop bounded to match v8; `AsyncPqfWriter` gained a debug-mode drop guard; CLI atomic output uses `O_EXCL`; `cargo vet` `audit-as-crates-io` policy gap fixed
- **Passphrase-only encryption (v10 format)**: `--passphrase` encrypt/decrypt mode with no ML-KEM step; Argon2id parameters in-header; `KdfLimitExceeded` ceiling; `--max-kdf-mem`/`--max-kdf-time` CLI flags
- **Compact recipient strings (**`pqf1…`**)**: `pqfile keygen` prints a Bech32m recipient string; `-r` accepts either PEM path or `pqf1…`; `pqfile fingerprint` subcommand
- `#![deny(unsafe_code)]` **at crate root** with narrow `#[allow(unsafe_code)]` on the sanctioned mmap call
- **Archive mtime and permissions restore**: `extract()` restores `mtime_secs` and `mode` from the PQFA manifest per entry
- `--force` **overwrite protection**: all CLI file-writing subcommands refuse to overwrite an existing output unless `--force` is passed (closes the silent-overwrite footgun from the 2026-07-01 audit)
- `pqfile check`: authenticates a `.pqf` end-to-end into a null sink without writing plaintext (named `check` rather than the roadmap's `verify` to avoid colliding with the existing signature-verification subcommand)
- **Windows ACL restriction on private key files**: `write_private_file` now strips inherited ACEs and leaves a single OWNER RIGHTS full-control ACE via `icacls`, mirroring the Unix 0600 behavior
- **Argon2id auto-calibration**: `pqfile doctor --calibrate [--target-ms N]` benchmarks the local machine and recommends `--kdf-mem`/`--kdf-time`; `encrypt --passphrase` accepts them via `encrypt_stream_passphrase_with_params`
- **Default recipient config file**: `~/.config/pqfile/config.toml` / `%APPDATA%\pqfile\config.toml` holding `recipient` and `key` defaults; explicit flags win; global `--no-config` opts out
- **Supply-chain hardening in release artifacts**: SLSA build provenance attestations (`actions/attest-build-provenance`) on all release artifacts, binaries built with `cargo auditable`, `cargo-vet` runs on PRs as well as pushes, and CI no longer skips itself on workflow-file changes. `cargo-vet` and `cargo-semver-checks` are now also required status checks on the "Protect main" ruleset.
- **Release binary tuning**: workspace `[profile.release]` with thin LTO, one codegen unit, and symbol stripping for smaller, faster native binaries and WASM bundle
- **SLH-DSA-SHAKE-192f signatures (FIPS 205)**: `sign-keygen --algorithm slh-dsa-shake-192f`; hash-based alternative to ML-DSA-65 at the same security category, auto-detected from the key's PEM tag by all sign/verify/signcrypt paths; plaintext, passphrase-encrypted, and hardware-backed key storage; 192f chosen over 192s because 192s signing is ~20× slower for no category gain
- **GUI** `<meta>` **CSP**: `pqfile-gui/index.html` carries an in-document Content-Security-Policy so the WASM app is protected even when served without the nginx header snippet
- **Keyfile as a second factor for passphrase mode**: `--keyfile <path>` on v10 `encrypt`/`decrypt`/`check` mixes the keyfile's SHA3-256 hash into the Argon2id derivation as the secret (pepper) input; the v10 header gained a flags byte (bit 0 = keyfile required) with unknown-bit rejection, and missing/superfluous keyfiles fail fast with dedicated errors (codes 23/24/25) before the KDF runs
- **Recursive directory packing with symlink/special-file rejection**: `pqfile archive --recursive` walks directory arguments (entry names keep the directory prefix, like tar), rejecting symlinks, devices, FIFOs, and sockets per-path, and rejecting duplicate entry names including case-insensitive collisions for all archives
- **Authenticated headers (**`VERSION_AUTH_BIT`**)**: new files set bit 7 of the version byte and bind `chunk_size`, `compression_algo`, and the v10 KDF fields into the chunk-0 key commitment (v3 definition, distinct domain separation), closing the compression-flag-flip gap; the version byte and `kem_variant` stay excluded so zero-copy `rekey`/`add-recipient` still work; old files remain readable and old pqfile versions reject new files with a clean `UnsupportedVersion`. Implemented without new per-layout version bytes, so no v5.0 wire-format redesign was needed (release versioning decision, 4.x vs 5.0, still open since older readers cannot read newly written files)
- `--qr` **on** `keygen` **and** `fingerprint`: renders the `pqf1…` recipient string as a terminal unicode QR code (uppercased for the denser QR alphanumeric mode; Bech32m is case-insensitive); goes to stderr under `--json`
- **Constant-time harness extension**: `examples/ct_decrypt.rs` (tamper-position classes on the AEAD reject path) and `examples/ct_passphrase.rs` (unrelated vs near-miss wrong passphrase on v10) join `ct_shamir.rs`; all three use the same dudect-style Welch t-test
- **Interactive no-args CLI mode**: running bare `pqfile` (no subcommand, no flags) drops into a guided prompt flow for encrypt/decrypt/keygen instead of clap's usage text; any argument (including `--help`) still takes the normal clap path. CLI-layer only, delegates to the same `run_`* functions as the flag-driven paths so behavior stays identical.
- **Plaintext length padding (Padmé)**: `pqfile::padding::padme_length`/`PadmeReader`/`TruncatingWriter` and `encrypt --pad` round the plaintext length to a coarser bucket (≤ ~12% overhead) before encryption, so ciphertext length no longer reveals the exact plaintext size. The true length still travels in the existing authenticated `original_size` header field; decrypt strips the padding back off by capping output at that field (a no-op for every non-padded file, so no `--pad` flag is needed at decrypt time). Incompatible with stdin input, empty files, `--mmap`, `--pipeline`, and `--compress` (compression would shrink the padding back down). Shipped without a wire-format change - no version bump required.
- **Magic-free stealth mode**: `encrypt --stealth` / `decrypt --stealth` / `check --stealth` (new library functions `encrypt_stream_stealth`/`decrypt_stream_stealth`) omit the `.pqf` magic, version byte, and KEM variant field entirely; wire layout is `KEM_CT || BASE_NONCE(8) || ORIGINAL_SIZE(8) || <chunked ciphertext>`, using the recipient's own key type (known to the decryptor already) instead of a variant field. Single recipient only; composes with `--pad`. There is nothing on the wire to auto-detect, so the caller must already know a file was written in stealth mode. See `docs/FORMAT.md` §6.
- **Compat-matrix vectors for v10, keyfile, stealth, and padding**: golden ciphertexts committed for all four post-v9 wire behaviors (`v10_passphrase.pqf`, `v10_keyfile.pqf` + keyfile, `stealth_768.pqf` + private key, `padme_768.pqf` + its own 37-byte plaintext that actually pads to 40); the padded vector locks in both that the header's `original_size` is the true length and that capping decrypt output at it recovers the exact input, and the keyfile vector locks in the fail-fast without its second factor. Standing policy: any future format addition lands with its vector in the same PR.
- `cargo-semver-checks` **CI job and pre-publish gate**: `ci.yml` job (with `--release-type minor`, so only breaking changes fail between releases) plus a gate in `publish.yml` before `cargo publish -p pqfile` using default inference against the stamped release version; library crate only, `--all-features` so the async surface is covered
- **Scheduled dependency advisory scan**: `.github/workflows/advisories.yml` runs `cargo deny check advisories` daily at 06:00 UTC and opens or updates a `security`-labeled tracking issue on failure instead of relying on the scheduled-failure email
- `zizmor` **workflow audit**: CI job (pinned `pipx install`, GH_TOKEN for the online audits) plus fixes for every finding: `persist-credentials: false` on all non-pushing checkouts, template-injection vectors (`github.ref_name`, release tag, mutants `extra_flags`, version step outputs) routed through `env:` vars, release-workflow Cargo caches removed entirely (cache poisoning would flow into provenance-attested binaries), and the accepted Trusted-Publishing finding documented in `.github/zizmor.yml`
- **Memory locking for in-flight secrets**: internal `LockedSecret<N>` (`pqfile/src/secret.rs`) holds secrets in `mlock`ed (`VirtualLock` on Windows, plus `MADV_DONTDUMP` on Linux) heap pages via `memsec`, zeroized before unlock on drop; covers session keys, KEM shared secrets, the HKDF hybrid secret, Argon2id output, and the keyfile pepper. Lock failure degrades softly to zeroize-only (small default `RLIMIT_MEMLOCK`/working-set quotas), unconditionally so on wasm32. Deliberately not covered: private-key seeds returned by the public `decrypt_seed`* functions (their `Zeroizing` return type is stable API) and expanded key objects (external `ml-kem`/`x25519-dalek` types); plaintext and chunk buffers are excluded by design, as they would exhaust the lock quota
- **FIDO2 hardware token second factor for v10 (**`fido2-enroll`**/**`--fido2` **CLI, desktop GUI)**: mirrors `--keyfile` in the same Argon2id pepper slot (new mutually-exclusive `V10_FLAG_FIDO2` header bit; `PqfileError::Fido2Required`/`Fido2NotRequired`, codes 26/27), but the secret comes from a physical security key's CTAP2 `hmac-secret` extension output instead of a file. New library API: `encrypt_stream_passphrase_fido2[_with_params]`, `decrypt_stream_passphrase_fido2[_with_limits]` - the core library stays free of any USB dependency; it only ever sees the already-derived 32-byte secret. `pqfile fido2-enroll` (CLI) / "Enroll New Token…" (desktop GUI) creates a non-resident CTAP2 credential requesting `hmac-secret` and writes an enrollment file (credential ID + a fresh random salt, not sensitive on its own since reproducing the secret needs the physical token) in the same text format both tools read. All USB HID code (`ctap-hid-fido2`) lives behind an off-by-default `fido2` cargo feature on both `pqfile-cli` and `pqfile-gui` (native target only; `pqfile-desktop` always enables it), so a normal build of either never needs `libudev-dev`/hidraw system packages; not available in the WASM web GUI (no hidapi target for browsers). Dedicated CI coverage compiles and unit-tests both crates' feature on every push without needing real hardware. Non-resident credentials were chosen deliberately over resident ones: no token resident-slot consumption, and every FIDO2 authenticator supports them.
- **v10 passphrase-only encryption in the desktop and web GUI**: previously CLI-only; the Encrypt/Decrypt tabs gained a Public Key / Passphrase mode toggle with the same optional keyfile/FIDO2 second factor as the CLI (FIDO2 desktop-only). Compression and stealth stay hidden in passphrase mode since neither has a library-level passphrase variant; Padmé padding composes with both modes. Batch encryption resolves the second factor (including any FIDO2 hardware touch) once per batch, not once per file.
- **Multithreaded zstd compression**: `encrypt_stream_compressed`'s zstd encoder now runs with the `zstdmt` Cargo feature enabled and sizes its worker count off `rayon::current_num_threads()`, so `encrypt --compress` on large compressible input is no longer single-threaded; still respects the CLI's `--threads` cap since that's what sizes the shared Rayon pool. No wire-format impact (still standard zstd frames); falls back to single-threaded when the pool has 1 thread.
- **CodeQL scanning**: enabled via the repository's default-setup toggle (no committed workflow file, so it needed nothing from this repo's CI files); Rust analysis running with `build-mode: none` alongside the existing SonarQube + clippy + fuzzing stack.
- **Deterministic benchmark gate (**`iai-callgrind`**)**: `pqfile/benches/iai.rs` benches the KEM (`keygen_bytes`), AEAD (`encrypt_bytes`/`decrypt_bytes` on a 64 KiB payload), header parsing (`inspect_stream`), and Shamir (`split_key`/`reconstruct_key`) paths under Valgrind/Callgrind via `#[library_benchmark]`, with setup functions keeping key generation and ciphertext prep outside the measured region. Gated at +/-5% instruction-count regression via `Callgrind::soft_limits([(EventKind::Ir, 5.0)])`, checked against the previous run's `target/iai/` baseline (restored by the existing `cargo-cache` action, Cargo.lock-keyed with a prefix fallback so it survives most dependency bumps). New `iai-bench` CI job installs `valgrind` from apt and `iai-callgrind-runner` pinned to the exact same version as the `iai-callgrind` dev-dependency (0.16.1 - a mismatch between the two is a hard error). Argon2id stays out of scope, as planned, since a memory-hard KDF under Valgrind's ~20x slowdown would dominate CI time for no signal. The existing criterion `crypto` bench and its wall-clock `bench` job in ci.yml are unchanged and still the source for human-readable local numbers.
- **Optional formally verified ML-KEM backend (**`libcrux-ml-kem`**, opt-in** `kem-libcrux` **feature)**: new `pqfile/src/kem_backend.rs` defines a `KemBackend` trait (`ek_from_seed`/`encapsulate`/`decapsulate`, all raw-byte in and out) with two implementors - `MlKemBackend` (RustCrypto `ml-kem`, always compiled, default) and `LibcruxBackend` (Cryspen's F*-verified `libcrux-ml-kem`, behind `kem-libcrux`). Every KEM call site across `encrypt.rs`, `decrypt.rs`, `keygen.rs`, `keys.rs`, and `shamir.rs` (two more files than the original scoping note anticipated) now goes through the trait instead of constructing `ml-kem` typed keys directly; `EkVariant`/`DkVariant` hold raw EK bytes and the 64-byte private seed respectively rather than backend-specific types. Plain random keygen (previously `Kem::generate_keypair()`) was unified onto the same seed-based path as import/hardware/reconstruction after confirming byte-for-byte equivalence: `generate_keypair`'s RNG draws `d` then `z` (32 bytes each) and reaches the same `generate_deterministic(d, z)` that `from_seed` reaches via `seed.split()`. No wire-format change - `pqfile/tests/kem_oracle.rs` already proved interchangeability, and the full compat-matrix vectors in `pqfile/tests/compat/` (golden ciphertexts from the default backend) pass unmodified under `--features kem-libcrux`. One real behavioral gap found and closed along the way: libcrux's raw `TryFrom<&[u8]>` public-key constructor is a length-only check, unlike `ml-kem`'s `EncapsulationKey::new()`, which also performs the FIPS 203 §7.2 "Encapsulation Key Check" (rejects out-of-range decoded coefficients); `LibcruxBackend::encapsulate` now calls a shared `validate_ek` helper that reuses `ml-kem`'s own constructor purely for this check (still always a dependency regardless of the feature) rather than re-implementing the coefficient bit-unpacking, so both backends reject the same malformed keys. New `kem-libcrux-check` CI job (mirrors the existing `fido2-check` pattern) runs clippy and the full `pqfile` test suite with the feature on; a normal build never pulls in the extra dependency tree. Caveat carried over honestly from the original scoping: independent analysis ([eprint 2026/192](https://eprint.iacr.org/2026/192.pdf)) found only ~58% of the Rust proof surface is actually SMT-checked and the NEON backend is admitted without proofs, so this is defense in depth, not a silver bullet.
- **Profile-guided optimization for the CLI release binary**: `release.yml`'s `build` job now does an instrument / train / merge / optimize cycle around `pqfile-cli` specifically, on all four native targets, using raw `-Cprofile-generate`/`-Cprofile-use` `RUSTFLAGS` rather than the `cargo-pgo` tool the original note suggested - `cargo-pgo` always shells out to plain `cargo build` internally (confirmed by reading its source), which is incompatible with the `cargo auditable build` this pipeline already uses to embed SBOM-scannable dependency metadata in shipped binaries; the manual RUSTFLAGS approach is the same official rustc PGO workflow cargo-pgo itself wraps, verified locally to compose cleanly with `cargo auditable` (`cargo audit bin` still finds the embedded dependency data on the optimized binary). New `scripts/pgo_workload.sh` trains on ML-KEM 512/768/1024/hybrid single-recipient roundtrips at two sizes, a multi-recipient roundtrip (exercises the AES-256-GCM session-key-wrap path), and a compressed roundtrip. **Scoped to the CLI only**, not `pqfile-desktop`: a GUI binary has no headless way to be driven in CI to collect profile data. **Does not cover v10** `--passphrase` **mode**: `rpassword` reads the controlling terminal device directly rather than stdin, so its prompt can't be scripted headlessly; the KDF that mode alone exercises (Argon2id) is already out of scope for instruction-level tuning per the iai-callgrind bench notes, since it's deliberately memory-hard, so the gap has low practical cost. The whole sequence runs inside a non-fatal wrapper: any failure (missing `llvm-profdata`, a workload error, a cross-compiled target's instrumented binary not being runnable on the build host, ...) falls back to the plain `cargo auditable build` that shipped before this existed, so a PGO-specific break can never fail a release - see the 2026-06-26 release-pipeline breakage for why that bar matters here. No PGO path for `pqfile-desktop` or the WASM bundle.
- **Signable public key certificates**: new `pqfile::cert` module (`issue_cert`/`verify_cert`/`Certificate`/`cert_use`) is a minimal PKI layer over the existing `sign` module - no new cryptographic primitive, just a signed, self-describing wrapper. A CA signing key (ML-DSA-65 or SLH-DSA-SHAKE-192f) signs a subject public key (any pqfile PEM: KEM/hybrid public key or a verifying key) together with a label, a validity window (`not_before`/`not_after`, Unix seconds, both inclusive), and an `allowed_use` bitmask (`ENCRYPT`/`SIGN`, combinable). The subject key's own PEM tag travels inside the signed body, so `verify_cert` hands back a ready-to-use PEM without the caller needing to know the key type in advance; the wire body is fully self-delimiting (no outer length prefix) so parsing and signing operate over the identical byte range. `pqfile issue-cert --ca-key <SK> --subject <PUBKEY|pqf1…> --label <TEXT> --allow-encrypt/--allow-sign [--not-before YYYY-MM-DD] --valid-days <N> -o <FILE>` creates one; `pqfile verify-cert --ca-key <VK> <FILE>` checks the signature and window and prints the label, validity, and allowed use. `pqfile encrypt -r <CERT> --ca-key <VK>` accepts a certificate directly in place of a raw recipient key: it verifies the cert, rejects it if `ENCRYPT` is not in `allowed_use` (new `PqfileError::CertUseNotPermitted`, code 29) or if the check time falls outside the window (new `PqfileError::CertNotValid`, code 28), and otherwise substitutes the embedded subject key transparently. Certificates do not chain and there is no revocation beyond the validity window (re-issue with a shorter window instead); a certified recipient key also skips the `.revoked`-sidecar check that a direct pubkey path gets, since there is no on-disk path to a sidecar for an embedded key.
- **Certificate support in** `sign`/`verify`/`signcrypt`/`signdecrypt` (2026-07-13): `verify -k`, `signcrypt -r`, and `signdecrypt -v` now accept a certificate PEM in the same slot as a raw key, each paired with a new `--ca-key <CA_VERIFYING_KEY>` flag; a shared `resolve_cert` CLI helper (also now backing `encrypt -r`, replacing that path's previous inline duplicate) verifies the cert, enforces the correct `cert_use` bit for that slot (`ENCRYPT` for `signcrypt -r`, `SIGN` for `verify -k`/`signdecrypt -v`), and substitutes the embedded subject key. `sign` itself takes a private signing key, which certificates don't cover, so it is unchanged.
- **GUI certificate support (desktop + web)** (2026-07-13): the Keys tab gained an "Issue / Verify Certificate" panel (`pqfile-gui/src/tabs/cert.rs`) with Issue/Verify sub-tabs mirroring `issue-cert`/`verify-cert` - issue takes a CA signing key (with optional passphrase), a subject public/verifying key, a label, and a validity length in days (always starting from "now"; an explicit `--not-before` override, unlike the CLI, was cut as unnecessary GUI surface), and writes the resulting certificate via the existing `save_result` helper (native file write or WASM download); verify takes a CA verifying key and a certificate file and displays the decoded label/validity window/allowed-use. The Encrypt tab's recipient picker also now accepts a certificate file directly (drag-and-drop or "+ Add Recipient…", both already routed through the same staging slot): a new CA-verifying-key row in the Recipients card resolves any staged PEM that `pqfile::cert::is_certificate` recognizes, checked for `ENCRYPT` use, before it becomes a recipient entry; resolution failures surface inline rather than failing silently. Shipped alongside two small pieces of reuse: a shared `current_unix_secs`/`unix_secs_to_ymd` pair in `pqfile-gui/src/types.rs` (the Settings tab's existing days-from-now date math was refactored onto the same reverse-JDN helper rather than keeping a third near-duplicate), and a pre-existing, unrelated native-build break (two `fido2`-gated field accesses missing their feature cfg, breaking every non-`fido2` native build) fixed in passing since it blocked verifying this work.
- **CLI/GUI surface-audit fixes** (2026-07-14): `pqfile --version` now works (`#[command(version)]` was simply missing from the top-level `Cli` struct); `pqfile add-recipient -k <PRIVKEY> -r <NEW_PUBKEY> <FILE>` exposes the existing, fully-tested `pqfile::add_recipient::add_recipient_stream` library function, which previously had no CLI subcommand or GUI entry point despite being listed as shipped - the GUI gained a matching "Add Recipient" sub-tab alongside Rekey on the Decrypt tab (`DecryptSubTab::AddRecipient`), mirroring the existing Rekey UI (old recipient's private key, new recipient's public key, target file, zero-copy). `pqfile man` (via `clap_mangen`) prints a roff man page, a natural companion to the existing `pqfile completions`. The four subcommands missing a top-level `--help` summary (`keygen`, `encrypt`, `decrypt`, `inspect`) now have one. `pqfile-cli`, `pqfile-gui`, and `pqfile-desktop` each gained a short crate-local `README.md` for GitHub browsing (only the `pqfile` library crate is published to crates.io and had one before). `Cargo.toml` gained two tracking comments: the `slh-dsa = "0.2.0-rc.5"` pin (still no stable 0.2.0 as of 2026-07-14, the only SLH-DSA backend) and an `ml-dsa >= 0.1.1` floor explanation (0.1.0-rc.3 and earlier carry a Decompose timing side-channel, RUSTSEC-2025-0144, and a signature-malleability regression, GHSA-5x2r-hc65-25f9, both fixed by 0.1.0-rc.4) so a future dependency-range loosening can't silently reintroduce either bug. Verified in passing: `async_io.rs`'s "zero test coverage" flagged during this review was a false alarm - it already has 14 `#[tokio::test]`s and CI's `cargo test --workspace --features pqfile/async` job already runs them on every push.
- `pqfile check --parallel` (2026-07-21): a first pass at this item (from the same day's codebase review) claimed `decrypt` had no `--parallel` path at all; closer reading of `pqfile-cli/src/commands/decrypt.rs` found `decrypt --parallel` already existed and worked, wired to the library's `decrypt_stream_parallel` - the real, narrower gap was that `check` (verify-without-writing-plaintext) always ran the serial `decrypt_stream` even on a large file. `check` now takes `--parallel` too, using the same `decrypt_stream_parallel`/`PARALLEL_BATCH_SIZE` path `decrypt` already used; falls back to the serial path transparently for non-v3/v5 formats, same as `decrypt --parallel` always did. ## v5.0 - Next major (breaking format changes)

These items require a new major version because they change the wire format or public API in a backward-incompatible way (or, for new KEM/cipher variants, produce files that older readers reject). Ranked.

- **X-Wing as the hybrid KEM (standards alignment)**
Replace the bespoke X25519+ML-KEM-768 combiner with [X-Wing](https://datatracker.ietf.org/doc/draft-connolly-cfrg-xwing-kem/), the IETF CFRG general-purpose PQ/T hybrid KEM, using the RustCrypto `[x-wing](https://github.com/RustCrypto/KEMs/tree/master/x-wing)` crate (built on the same `ml-kem` and `x25519-dalek` pqfile already depends on). X-Wing carries a formal security proof (secure if SHA-3 and either component is secure) and is on an RFC track, which buys interoperability and external review that a homegrown combiner never gets. Technically this could ship additively as a new KEM variant ID in 4.x, but since older readers cannot read the files it belongs with the other compatibility-affecting work. The existing hybrid variant stays readable forever. Code anchors: the current bespoke combiner is `hybrid_hkdf` in `pqfile/src/format.rs` (HKDF-SHA256 over both shared secrets), hybrid keygen lives in `pqfile/src/keygen.rs`, and KEM variant IDs are defined in `format.rs`; X-Wing replaces the combiner and the two-ciphertext slot layout with the crate's single opaque KEM, so the recipient-slot writing and parsing code changes too. Status as of 2026-07-13: still an individual Internet-Draft (`draft-connolly-cfrg-xwing-kem-10`), not yet adopted by an IETF working group or issued as an RFC; the "to be removed before publishing as an RFC" note is still present in the draft. Worth tracking but not yet blocking - the RustCrypto crate already tracks the draft closely enough to prototype against.
- **Per-file entry AEAD in archives (PQFA v2)**
The current `.pqfa` format authenticates the entire archive before any file is extracted, which requires buffering the full ciphertext in memory for in-memory extractions. A PQFA v2 layout gives each file entry its own AEAD tag derived from the session key and the entry index, so individual files can be extracted and verified without loading the whole archive. Design notes for when this happens: bind both the entry index and the entry name into each entry's AAD (index prevents undetected reordering, name prevents undetected renames), authenticate the manifest on its own before streaming any entry, and keep the per-entry `mtime_secs`/`mode` restore working from the v1 work. The archive code is isolated in `pqfile/src/archive.rs`.
- `PqfileError` **refinement** *(substantially complete)*
`Truncated`, `UnsupportedVersion`, and `NoMatchingRecipient { slots_tried }` already exist as distinct variants, and `DecryptionFailure` is now returned only for genuine AEAD tag mismatches (plus deliberate anti-oracle collapsing of malformed-ciphertext cases). The only remaining piece of the original item is renaming `DecryptionFailure` → `AuthenticationFailure`, a pure rename whose API break buys no new information for callers; do it only if a v5.0 major happens for other reasons.
- **Misuse-resistant nonces (nonce-SIV construction)**
Replace random nonces with synthetic nonces derived from a hash of the session key and plaintext chunk (a simplified SIV mode). With random nonces, a nonce collision is possible if the same key encrypts a very large number of chunks; SIV derivation makes collision probability zero regardless of how many files are encrypted under a given session key. This is a format break because the nonce field changes meaning in the chunk header. Lower priority than it may sound: every file already gets a fresh session key, so the collision scenario this defends against is already negligible in practice.
- **AEGIS as an optional AEAD suite**
[AEGIS-128L / AEGIS-128X / AEGIS-256](https://github.com/jedisct1/rust-aegis) (CFRG draft `draft-irtf-cfrg-aegis-aead`) is dramatically faster than both AES-GCM and ChaCha20-Poly1305 on CPUs with AES acceleration, natively key-committing (pqfile currently bolts commitment on via the chunk-0 AAD), and has a large nonce space. A new cipher ID in the header means older readers reject the files, hence v5.0. Caveats that keep it below X-Wing: the performant path of the `aegis` crate links C (`libaegis`) via `cc` while the pure-Rust fallback is much slower, the WASM story is weak, and ChaCha20-Poly1305 already saturates most storage I/O, so the practical win is narrower than the benchmark gap suggests.

### 1. Time-locked encryption *(shipped 2026-07-15, pure time-lock only)*

Shipped as the v11 format behind a new off-by-default `tlock` Cargo feature: `encrypt --tlock-round <ROUND>` / `decrypt --tlock` / `check --tlock`, plus `pqfile tlock round "24h"|<RFC3339>` to resolve a human time expression to a round number. Uses `tlock` + `drand_core` against the League of Entropy `quicknet` mainnet chain by default. See `docs/CHANGELOG.md` (Unreleased) and `docs/FORMAT.md` §5.12 for full details.

Scope cut made during implementation, worth recording so it isn't re-litigated: this ships **pure** time-lock (no recipient key pair at all - anyone with the ciphertext can decrypt once the round fires), not the "wrap the session key alongside a normal recipient slot" shape gestured at below. Combining a tlock-derived secret with a real KEM recipient's shared secret in one key schedule (an AND-gate: needs both the round *and* a specific private key) is a materially different design - not scoped further here, but a natural follow-up if the pure form sees real use. The not-post-quantum caveat (drand's tlock scheme is BLS12-381 pairing-based) is preserved and documented at every user-facing surface (README, FORMAT.md, CHANGELOG).

Testing note for future maintainers: unlike every other format, `pqfile/tests/compat/` has no `tlock_*.pqf` golden fixture. `decrypt_stream_tlock`'s only public entry point always fetches a live beacon signature over the network, so a `tests/compat.rs`-style vector would need the same private-bypass trick as the in-module tests below to stay offline, gaining no additional wire-format-drift protection. Coverage instead lives in `pqfile/src/tlock.rs`'s own test module: `full_stream_roundtrip_with_pinned_signature` exercises the real header + chunk engine end-to-end against a pinned, already-elapsed quicknet round's real signature (round 1000), and two `#[ignore]`d tests hit the live relay (a real historical round, and a deliberately-far-future round to check the `TlockRoundNotReached` mapping) - run manually with `--ignored`, never in CI, same convention as the `ct_*.rs` dudect harnesses.

### 2. age ecosystem interoperability

age v1.3.0 ships native post-quantum hybrid ML-KEM-768+X25519 recipients, and the [age plugin protocol](https://words.filippo.io/age-plugins/) makes third-party recipient types first-class in every age client (including rage, the Rust implementation). An `age-plugin-pqfile` binary exposing pqfile identities as age recipients would put pqfile keys inside the largest modern file-encryption ecosystem without users switching tools. Independently worth stealing: age's `RecipientWithLabels` anti-downgrade mechanism, where a recipient labeled `postquantum` refuses to be mixed with weaker recipients in one file; pqfile's multi-recipient modes currently have no equivalent policy check when mixing, say, an ML-KEM-1024 slot with an ML-KEM-512 slot.

### 3. OpenPGP-PQC interoperability *(added 2026-07-13)*

`[draft-ietf-openpgp-pqc](https://datatracker.ietf.org/doc/draft-ietf-openpgp-pqc/)` (extending RFC 9580) defines composite ML-KEM+X25519 encryption and composite ML-DSA+Ed25519 signatures for OpenPGP, alongside standalone SLH-DSA; it reached draft -17 on 2026-01-13 and is expected to publish in H1 2026, with Sequoia PGP committed to shipping support shortly after. This is a much larger existing user base than age's plugin ecosystem (item 2), and GnuPG/Sequoia users are exactly the population most likely to already care about post-quantum key material. Shape is different from the age plugin approach, though: there's no third-party-recipient extension point, so this would mean either exporting/importing pqfile key material as OpenPGP-PQC-compatible packets (a real ASN.1/OpenPGP-packet-format effort, not a thin adapter) or, more realistically, a standalone `pqfile pgp-export`/`pgp-import` conversion utility scoped to the composite-key case only. Track the draft to final publication before scoping further; revisit alongside the FN-DSA item below since both are pinned on a NIST/IETF document finalizing in a similar window.

**Status update (2026-07-20)**: the draft has moved to **AUTH48** (final copy-edit stage before publication) with an RFC number already assigned - **RFC 9980**. This is the exact publication trigger the note above was waiting on; the item should move up in priority at the next planning pass. The scoping problem is otherwise unchanged: no third-party-recipient extension point, so this stays an export/import conversion utility rather than a thin adapter.

**Status update (2026-07-21): RFC 9980 published (June 2026, Standards Track) - scoped, and deferred.** A detailed pass against pqfile's actual key types found the real overlap is much narrower than the shape assumed above:

- **Hybrid encryption keys (`X25519+ML-KEM-768`) are the one clean match.** pqfile already stores these as a raw X25519 public key appended to a raw ML-KEM-768 encapsulation key (private side: a 32-byte X25519 scalar plus a 64-byte ML-KEM seed - see `pqfile/src/keygen.rs`). RFC 9980's algorithm ID 35 is exactly ML-KEM-768+X25519, and it's the RFC's one *mandatory-to-implement* composite. A key-material export/import is genuinely reachable here.
- **Plain ML-KEM-512/768/1024 (non-hybrid) keys have no OpenPGP-PQC equivalent at all.** RFC 9980 defines no standalone ML-KEM option - composite-with-ECDH is the only encryption path in the whole spec.
- **ML-DSA-65 signing keys are not a straight export.** RFC 9980 mandates ML-DSA-65 only paired with a fresh Ed25519 key (composite signature, both components must verify), so an existing pqfile ML-DSA-65 key can't become an OpenPGP key on its own - it would need a newly-minted companion Ed25519 key, which is really "issue a new OpenPGP identity that happens to reuse your ML-DSA key," not a conversion of the existing one.
- **SLH-DSA-SHAKE-192f signing keys have no mapping, full stop.** RFC 9980 specifies exactly three standalone SLH-DSA options - SHAKE-128s, SHAKE-128f, and SHAKE-256s (algorithm IDs 32-34) - and no 192-bit security level at all. pqfile's own SLH-DSA parameter set simply isn't representable in OpenPGP-PQC as it stands.

So a conversion utility's realistic scope collapsed to *hybrid encryption keys only* - narrower than "the composite-key case" phrasing above implied, since that reads as covering both KEM and signature composites. Separately, the obvious implementation dependency, `sequoia-openpgp`, only has PQC support in a pre-release fork (`2.2.0-pqc.1`, needing `--features crypto-openssl`, a system OpenSSL dependency) with no stable-release date even now that the RFC is published - conflicts with this project's consistent rustls-only stance (`tlock`/`update-check` both deliberately avoided system OpenSSL via `ureq`+rustls).

**Decision: parked, not building the narrow version.** Given signing-key interop - arguably the more valuable half, since GnuPG/Sequoia users care at least as much about verifying mail signatures as encrypting to a recipient - isn't reachable at all today, and the one clean win (hybrid encryption keys) would still mean depending on an unstable OpenSSL-requiring pre-release crate, this isn't worth building yet. Revisit when either: (a) `sequoia-openpgp` ships a stable, non-`crypto-openssl`-only PQC release, or (b) a future OpenPGP-PQC revision adds standalone ML-KEM or a 192-bit SLH-DSA parameter set, meaningfully widening what a conversion utility could actually cover.

### 4. FN-DSA (Falcon) signatures

FIPS 206 went to draft approval in August 2025 with the final standard expected late 2026 or early 2027. FN-DSA signatures are ~666 bytes versus ~3.3 KB for ML-DSA-65, a major win for signcrypt overhead and QR-code-sized artifacts. Thomas Pornin's `[rust-fn-dsa](https://github.com/pornin/rust-fn-dsa)` is high quality and tracks the draft. The PEM-tag-based algorithm auto-detection added for SLH-DSA means a third signature algorithm slots into every sign/verify/signcrypt path the same way. Blocked on: the standard finalizing, and the crate stabilizing against the final test vectors. Revisit each quarter. Status as of 2026-07-13: unchanged from the prior review - NIST's IPD is still open for public review, no published FIPS 206 yet.

### 5. Threshold ML-DSA signing *(added 2026-07-13)*

Extend pqfile's existing M-of-N story (Shamir threshold **decryption**) to threshold **signing**: split a CA or long-term signing key across N custodians such that any K can jointly produce a valid, standard-verifying ML-DSA signature without ever reconstructing the private key on one machine. The direct motivating use case is the new `pqfile issue-cert --ca-key`: today the CA private key is a single file an operator must protect entirely on their own, which is a weak link for anything acting as a real certificate authority. This is genuinely research-grade right now, not a "pick a crate" task: 2026 saw several competing constructions (Mithril, Hermine, Quorus, and "Masked Threshold ML-DSA" via Shamir nonce DKG) but none has a mature, audited Rust implementation, and per the NIST CSRC threshold-signatures track most existing threshold schemes are still incompatible with the standardized FIPS 204 verifier - "Masked Threshold ML-DSA" is notable specifically because it claims standard-verifier compatibility. Revisit in 6-12 months once one of these constructions has a real crate; premature to scope further today.

**Status update (2026-07-20)**: a real crate now exists - `[threshold-ml-dsa](https://crates.io/crates/threshold-ml-dsa)` (lattice-safe org), a paper-faithful implementation of the Mithril construction (ePrint 2026/013) for threshold ML-DSA-44: FIPS 204 bit-for-bit-verifier-compatible output, `no_std`-compatible, zeroize-on-drop, K-parallel repetitions with hyperball rejection sampling, scaling from 2-of-3 to 32-of-45 thresholds at sub-100ms latency. This crosses the "no mature Rust implementation" blocker named above, so the item is now a concrete "prototype against this crate" task rather than a wait-for-the-field one - but it is not independently audited, so that should be a prerequisite (or at least an explicit accepted-risk call) before it backs a real CA signing key, not a reason to defer further research.

**Status update (2026-07-21): re-checked against the crate's actual README/docs.rs (v0.3.6) - the 2026-07-20 note above overstated readiness, correcting here.** The real supported range is **15 (T,N) configurations from (2,2) to (6,6) - max 6 total parties**, not "2-of-3 to 32-of-45"; that figure appears to have been a misread, possibly of the underlying paper's theoretical range rather than what the shipped SDK exposes. Beyond the scale correction, several harder problems surfaced against pqfile's actual use case:

- **Fresh keygen only, not key splitting.** `ThresholdMlDsa44Sdk::from_seed` generates independent threshold secrets from scratch; it does not decompose an *existing* ML-DSA private key into shares. The motivating problem above - "today's `issue-cert --ca-key` is a single file" - isn't solvable for a CA that already exists this way; it only helps someone setting up a brand-new CA from day one.
- **ML-DSA-44 only, not 65.** pqfile's `cert` module requires ML-DSA-65 (Category 3) or SLH-DSA-SHAKE-192f for CA keys today. This crate is Category 2 only, so adopting it means either a security-category downgrade for threshold CAs specifically, or a new, lower-security CA key type alongside the existing ones.
- **Explicitly not constant-time.** The README states hyperball sampling uses floating-point (`f64`/`libm`) and "is not strictly constant-time," recommending deployments "isolate party execution" - a real regression against this project's own constant-time bar (three dudect harnesses elsewhere), and not something a CLI can practically guarantee for the caller.
- **A second, independent ML-DSA implementation.** Depends on `dilithium-rs`, not the RustCrypto `ml-dsa` pqfile already uses everywhere else - two unaudited ML-DSA implementations in the tree instead of one.
- **Real multi-machine deployment needs the caller to build the transport.** The 3-round commit/reveal/respond protocol is only fully wired for single-process demos; genuine separate-custodian deployment means designing and implementing authenticated networking between parties, outside the crate's scope.

**Decision: parked, not prototyping against this crate now.** The combination of small max N, Category 2-only, fresh-keygen-only (doesn't protect an existing CA key, the actual motivating problem), unaudited, and explicitly non-constant-time is closer to "the field now has one candidate crate" than "ready to build a real feature on." Revisit once N scales further, ML-DSA-65 is supported, key-splitting (not just fresh keygen) is possible, or an independent audit lands.

### 6. Sealed sender *(shipped 2026-07-15)*

Shipped as `pqfile::sealed_sender` (`identity_keygen[_bytes]`, `seal[_bytes]`, `unseal_bytes`), CLI subcommands `identity-keygen`/`seal`/`unseal`, and a GUI "Sealed Sender" tab (desktop + web) with Identity Keys/Seal/Unseal sub-tabs. No wire-format change - a sealed-sender file is a standard v3 `.pqf` file whose plaintext payload is `tag ++ original plaintext` (`docs/FORMAT.md` §9).

Scope note: the mechanism that shipped differs from the sketch above. Rather than an HKDF-derived one-time *signing* key pair, it uses a static-static X25519 Diffie-Hellman between a new, separate long-term *identity* key pair for each party (§6.6), and authenticates a SHA3-256 tag over the plaintext rather than an ML-DSA/SLH-DSA signature. The static identity DH shape was chosen over the ephemeral-signing-key sketch because it is simpler to implement correctly (no ephemeral key material to generate, sign with, and then discard per file) and because it more directly guarantees deniability: since either party's private key plus the other's public key reproduces the identical tag, there is no signature object anywhere that a future key-compromise or protocol bug could turn into non-repudiable evidence. The identity key pair is intentionally separate from both the ML-KEM encryption key and any ML-DSA/SLH-DSA signing key, so using sealed sender never affects the non-repudiation properties of `signcrypt`. See `docs/CHANGELOG.md` (Unreleased) for the full CLI/library/GUI surface.

Compat-vector note: no new `pqfile/tests/compat/` golden fixture was added, matching the existing precedent for `signcrypt` (also payload-convention-only, no dedicated vector). The standing "any format addition lands with its vector" policy above (§v4.x Planned) is about wire-format drift; sealed sender's tag ++ plaintext convention lives entirely above `format.rs` and produces an ordinary v3 file already covered by the `v3_*.pqf` vectors, so there is no new byte layout for a vector to protect. Round-trip and cross-key-mismatch coverage instead lives in `sealed_sender.rs`'s own test module, same convention as `signcrypt.rs`.

### 10. Hardware Security Module (HSM) / PKCS#11 support *(added 2026-07-13)*

pqfile's current "hardware-backed key" story is the OS credential store (Windows DPAPI, macOS Keychain, Linux Secret Service) - convenient, but not a real HSM or smartcard boundary, and not what an organization with a compliance requirement for hardware key custody actually needs. PKCS#11 v3.2 now standardizes mechanisms for ML-KEM, ML-DSA, and SLH-DSA (without external-mu), and 2025-2026 saw several HSM vendors (Entrust nShield 5, Thales Luna G7/K7, Marvell LiquidSecurity 2, Securosys, Utimaco) obtain CAVP certification for the NIST PQC algorithms with FIPS 140-3 validation in progress. The `[cryptoki](https://docs.rs/cryptoki)` crate is a maintained Rust PKCS#11 binding. Ranked below the language-bindings and shell-integration items because deployed PQC-capable HSM hardware is still early - not every vendor ships it yet - so the addressable user base today is small; revisit as hardware availability broadens. Would slot in as a new key-source alongside the existing plaintext/passphrase-encrypted/OS-credential-store options, additive and non-breaking to the wire format.

### 11. Certificate revocation *(shipped 2026-07-15)*

Shipped as the lightest-weight design sketched below: `pqfile::cert::revoke_cert`/`verify_revocation_list`/`check_cert_not_revoked`, CLI `pqfile revoke-cert`, and an optional `--revocations <FILE>` flag on every command that already resolves a certificate (`encrypt -r`, `verify -k`, `signcrypt -r`, `signdecrypt -v`, `seal -r`, `verify-cert`). A revocation list is a CA-signed sequence of `(cert_id, revoked_at, reason)` entries - a compact analogue of an X.509 CRL - consulted only when the caller supplies one, mirroring the `.revoked` sidecar convention raw keys already use. `cert_id` is SHA3-256 of the certificate's own signed body rather than a new CA-assigned serial number field: `Certificate`'s existing fields (label, validity window, allowed use, subject key) already uniquely identify what's being revoked in every case that matters, so no format change to `Certificate` itself was needed. Full OCSP-style online responder infrastructure remains out of scope, as originally scoped - offline, file-based revocation checking fits pqfile's usage pattern. See `docs/CHANGELOG.md` (Unreleased) and `docs/FORMAT.md` §6.5 for full details.

### 12. Encrypted audit log *(shipped 2026-07-22)*

Shipped as `pqfile::audit` (`AuditRecord`, `build_entry`, `verify_log`, `audit` cargo feature) plus CLI `--audit-log`/`--audit-key`/`--audit-recipient` on `encrypt`/`decrypt` and a new `pqfile audit-verify` subcommand. Each record - timestamp, command, a BLAKE3 file fingerprint, and the key's fingerprint - is signed with the operator's own ML-DSA/SLH-DSA key, then encrypted to a separate auditor's ML-KEM public key, so only the auditor can read the log while a hash chain (each record links to the BLAKE3 hash of the previous *signed* record, per the standing BLAKE3 guideline above) lets anyone holding the operator's verifying key detect silent deletion or reordering without the auditor's private key at all. One design wrinkle not anticipated in the original scoping: since only the auditor can decrypt the log, the *operator* appending a new record has no way to decrypt the log's own tail to learn the previous record's chain hash - resolved with a small non-secret `<log>.chainhash` sidecar (32 raw hash bytes) that `verify_log` itself never needs, since it recomputes the chain from scratch while decrypting. Scoped to encrypt/decrypt only, matching the item's own wording, not every subcommand. `pqfile-gui` support is native-only (Settings-tab section): an append-only log needs real persistent storage, which the web build's download-only file model can't provide, unlike the FEC sidecar (item 21), a one-time artifact browser downloads handle fine.

**Follow-up correction (2026-07-22 audit)**: the chain-link check alone cannot detect a whole entry deleted off the *end* of the log - only reordering or a gap followed by another entry. `verify_log` gained an `expected_tip` parameter (`audit-verify --expect-tip <HEX>`) to close this: it rejects a log whose final chain hash doesn't match a value the caller already trusts independently, and every `audit-verify` run prints that final hash so it can be saved and supplied on the next run. The `<log>.chainhash` sidecar was never fit for this - it shares the log's own trust boundary, so an operator who can truncate the log can equally overwrite the sidecar next to it. See `docs/CHANGELOG.md` (Unreleased).

### 13. Split ciphertext storage

A mode where the raw ciphertext bytes are split across N output files using a secret sharing scheme (or simpler XOR splitting for K=N), requiring any K files to reconstruct. Different from key splitting: the key stays intact and the payload itself is distributed. Useful for backup scenarios where the ciphertext is spread across cloud providers that are mutually untrusted; no single provider has a usable ciphertext.

### 14. Key ceremony tooling

An interactive guided ceremony mode for high-assurance key generation. Multiple participants each contribute entropy combined via SHA3-256 before seeding key generation so no single participant can bias the result. The ceremony log records each participant's entropy hash, the combined seed hash, and the resulting public key fingerprint.

### 15. Attribute-based access control policies

Go beyond M-of-N threshold decryption to support Boolean access policies: "decrypt if holder of key A AND key B, OR key C." Each policy node is an encrypted share of the session key. Evaluation is a tree walk using Shamir recombination at AND nodes and branch selection at OR nodes.

### 16. Web extension / browser integration

A browser extension (Chrome / Firefox) that embeds the existing WASM core and adds an "Encrypt" action to file-attachment dialogs and an "Encrypt text" context menu item. Encryption runs entirely in the browser process; no data is sent to a server.

### 17. Deniable encryption

Produce a `.pqf` file that yields two valid, indistinguishable plaintexts: a real one under the primary key and a decoy under a duress key. Both decrypt without error and leave no detectable marker distinguishing which is real. VeraCrypt offers this for full-disk volumes but no post-quantum file encryptor provides it. The design challenge is two independently valid ML-KEM shared secrets each mapping to a distinct AEAD layer, with a header that reveals nothing about which layer is authoritative. *(2026-07-14 addition:)* VeraCrypt's specific mechanic is worth studying as an alternative shape to the single-file dual-layer design above: a "hidden volume" is written into the free-space slack of an outer volume that itself holds real (if less sensitive) content, so revealing only the outer passphrase under coercion is itself plausible rather than obviously partial. Combined with pqfile's existing Padmé length-padding, an outer `.pqf` padded well beyond its real content, with a hidden inner ciphertext occupying the padding slack, could reuse `padding.rs` machinery rather than requiring a wholly new dual-AEAD-layer format.

### 18. Forward-secret file exchange protocol

A stateful protocol built on pqfile that provides forward secrecy for an ongoing file exchange session between two parties. Each exchange ratchets a shared root secret forward using a new ML-KEM encapsulation, so compromise of the current session key does not expose previously exchanged files. State lives in a small JSON ratchet file alongside the key pair.

### 19. Proxy re-encryption

Generate a re-encryption key `rk(A -> B)` from private key A and public key B. A proxy holding only `rk` can transform a ciphertext encrypted for A into one encrypted for B, without ever seeing the plaintext or either private key. Useful for delegated access: a file server can re-encrypt stored files on behalf of a new recipient without the sender needing to re-encrypt manually. Ranked last among the cryptographic items because no practical post-quantum PRE construction with a mature implementation exists; the known lattice-based schemes are research-grade, and falling back to a classical ECC-based PRE would break the project's post-quantum story.

### 21. Forward-error-correction for cold-storage resilience *(shipped 2026-07-22)*

Shipped as `pqfile::fec` (`generate_sidecar`, `FecRepairReader`, `fec` cargo feature) plus `--fec` on `encrypt`/`decrypt`/`check`. Scope correction made during implementation: the original note described parity "computed *before* encryption," which reads as protecting the plaintext - what actually ships (matching Picocrypt, the cited prior art, and the only design that makes "repair happens before the AEAD check runs" coherent) computes Reed-Solomon parity over the **ciphertext** bytes, the ones actually vulnerable to bit rot on disk. Uses classical Reed-Solomon BCH error *correction* (the [`reed-solomon`](https://crates.io/crates/reed-solomon) crate) over fixed 128-byte blocks with 8 ECC bytes each - correcting up to 4 corrupted bytes anywhere in a block without knowing their positions in advance, the same ratio Picocrypt itself uses (roughly 3% tolerance before giving up). A second scope simplification: parity is a **separate sidecar file** (`<output>.pqf.fec`), not interleaved into the `.pqf` file itself - computed as a post-pass over the finished output, with zero awareness of `.pqf` structure at all. This is what makes it apply uniformly to every format version (header included) with no wire-format change, unlike embedding parity in a new version layout would have required. `FecRepairReader` wraps the ciphertext reader and repairs blocks transparently before any decrypt/check path sees them; an uncorrectable block passes through unchanged rather than erroring, so a genuine tamper failure still fails exactly as it would without FEC - purely additive to authentication, as originally scoped. `pqfile-gui`'s own `fec` feature is on by default (no platform restriction): an Encrypt-tab checkbox, and native decrypt auto-detects a same-named `.fec` file next to the loaded input (the web build has no analogous auto-detection, since there is no filesystem to look beside). See `docs/CHANGELOG.md` (Unreleased).

### 22. Content-defined chunking and dedup for PQFA archives *(added 2026-07-14)*

The `.pqfa` archive format packs files as opaque entries with no cross-entry structure, so re-archiving a directory where only a few files changed re-encrypts and re-stores everything. restic, Borg, and Kopia all chunk file content with a rolling hash (Buzhash/FastCDC-style) and store each unique chunk exactly once, referenced by its hash - repeated or overlapping backups shrink dramatically. Natural pairing with the already-planned PQFA v2 per-entry AEAD (see the v5.0 section): a chunk index keyed by BLAKE3(chunk) (per the standing BLAKE3-for-non-format-hashing guideline above, since chunk identity never touches the wire format's authentication) would let PQFA store each unique chunk once and support incremental re-encryption of only the changed chunks on repeated archive operations. Scope carefully before starting: chunk-level dedup is a bigger design surface than PQFA v2's per-entry AEAD alone, and interacts with it (chunk boundaries vs. entry boundaries are different concerns).

### 23. Steganographic key backup *(shipped 2026-07-16)*

Shipped as `pqfile::stego` (`bury`/`exhume`/`capacity`) and CLI subcommands `pqfile bury --image <COVER> <FILE> -o <OUT.png>` / `pqfile exhume <STEGO_IMAGE> -o <OUT_FILE>`, behind a new off-by-default `stego` Cargo feature (pulls in the `image` crate's PNG/JPEG codecs plus `blake3`, which a normal build never pays for). CLI subcommands are flat (`bury`/`exhume`), not the `pqfile key bury`/`pqfile key exhume` grouping originally sketched, to match this CLI's existing style (`keygen`, `issue-cert`, `revoke-cert` are all top-level rather than grouped under a verb).

**GUI wiring (same day, follow-up)**: unlike the native-only FIDO2/keyfile second factors, this has no platform restriction (no USB HID, no OS credential store), so `pqfile-gui` gained its own `stego` feature defaulting *on* - both the desktop app and the web (`trunk build`) app get a new collapsible "Steganographic Key Backup" panel in the Keys tab (Bury/Exhume sub-tabs, mirroring the existing Certificate panel's `CollapsingHeader` placement) with no extra build flags needed. Verified by actually launching `pqfile-desktop` and screenshotting the panel, plus a new `stego_bury_exhume_roundtrip_via_gui` test that drives the real button-click handlers end-to-end rather than just the library.

Scope correction made during implementation: the original note described LSB-embedding "inside an ordinary JPEG via steghide," but naive pixel-LSB embedding cannot survive JPEG's lossy DCT re-encode - steghide's real JPEG support instead embeds in the DCT coefficients themselves, a materially larger undertaking (a `dct_io`-crate-based coefficient-level implementation was scoped but deliberately not attempted here). What shipped instead: `bury` accepts a cover image in any `image`-crate-decodable format including JPEG, decodes it to raw RGB8 pixels, and always re-encodes the result as PNG (lossless) regardless of the cover's original format - so a JPEG photo works fine as *input*, but the output is always `.png` (the CLI rejects a non-`.png` `-o` path with a clear error rather than silently producing a `.png` file at a `.jpg` path).

Format (inside the pixel data, not a pqfile wire format), as revised by the 2026-07-17 security audit below: `SALT(16) || ENC(MAGIC("PQST") || LEN(u32 LE) || MAC(keyed-BLAKE3-32) || PAYLOAD)`, embedded one bit per byte into the LSB of the cover's RGB8 pixel bytes (alpha dropped), sequentially from the start of the buffer, where `ENC` is an XOR with a BLAKE3-XOF keystream derived from a passphrase (Argon2id at parameters frozen forever for this scheme, then BLAKE3 subkey split for keystream + MAC keys). `exhume` collapses every failure mode - wrong passphrase, wrong image, corrupted/edited stego image, or a recorded length that doesn't fit the image's capacity - into one `StegoPayloadNotFound` error (codes 37-39 cover capacity/not-found/invalid-image); with keyed detection the collapse is load-bearing, since distinguishing "wrong passphrase" from "nothing here" would leak exactly the signal the scheme withholds. BLAKE3 was used per the standing BLAKE3-for-non-format-hashing guideline above.

**Security audit revision (2026-07-17)**: the scheme as first shipped embedded a *plaintext* magic, length, and checksum, so anyone with the (public) pqfile tool could detect and extract a buried payload in milliseconds with no secret at all - the original "nothing distinguishes a buried image from an ordinary one without running `exhume` against it" claim was hollow, because running `exhume` was free. Reworked before first release to keyed detection: `bury`/`exhume` now take a passphrase, everything after a random salt is keystream-encrypted, and a wrong passphrase is indistinguishable from an absent payload. The same pass fixed a 32-bit (wasm) integer-wrap panic on a crafted LEN field (now u64 arithmetic), added decode dimension caps (16384px/side, 100 MP) against decompression-bomb covers, moved the CLI's `exhume` output onto the atomic owner-only `write_private_file` path, zeroized all payload/framing buffers, and added a `fuzz_exhume` target. Still deliberately not done: bits remain sequential rather than at a passphrase-seeded pseudo-random offset, so a chi-square attack on the altered region can flag that *something* is embedded - the passphrase prevents confirming or recovering *what*, and scattering bits would only shrink the statistical signal, not eliminate it.

### 24. NIST additional PQC signatures ("on-ramp": HAWK, SQIsign, MAYO, etc.) - watch only *(added 2026-07-14)*

NIST's post-ML-DSA/SLH-DSA/FN-DSA signature track (distinct from all three already tracked above) advanced 9 candidates - FAEST, HAWK, MAYO, MQOM, QR-UOV, SDitH, SNOVA, SQIsign, and UOV - to Round 3 on 2026-05-14 (NIST IR 8610); CROSS was eliminated after a parameter-breaking attack forced an uncompetitive revision. HAWK is the sole lattice-based survivor at a notably smaller signature size than ML-DSA (555 bytes at category 1); SQIsign posted large signing/verification speedups since Round 1. Realistic standardization is 2028-2030 given Round 3's ~2-year evaluation window and another NIST conference planned for H1 2027. Nothing actionable today - recorded here so the on-ramp isn't silently absent from this document - but worth a check-in alongside the FN-DSA and OpenPGP-PQC items each time those are revisited.

### 25. Transparent cloud-sync/backup overlay (rclone-crypt / gocryptfs style) *(added 2026-07-20)*

Both `rclone` ([issue #3567](https://github.com/rclone/rclone/issues/3567)) and `restic` ([issue #4738](https://github.com/restic/restic/issues/4738)) have long-open, unresolved feature requests for post-quantum encryption, and the broader 2026 backup-tool ecosystem (Restic, BorgBackup, Kopia, Duplicati) has confirmed no PQC plans - AES-256-GCM/ChaCha20-Poly1305 remain the norm there with no near-term movement. Rather than waiting on any of those projects, or reimplementing sync/dedup logic pqfile has no reason to own, a transparent overlay mirrors a plaintext directory tree onto a directory of `.pqf` files one-to-one (à la gocryptfs or rclone's own `crypt` remote), mounted via FUSE on Linux/macOS and Dokan or WinFsp on Windows. Any file-based sync or backup tool - `rclone sync`, Restic, a cloud-drive client, plain `rsync` - then only ever sees opaque per-file ciphertext, without any of those tools needing to add PQC themselves. This is a distribution channel none of the other 24 items target: it puts pqfile in the workflow of every existing backup/sync user rather than requiring them to adopt a new tool. Natural pairing with the already-planned PQFA v2 per-entry AEAD and content-defined-chunking/dedup work (items in the v5.0 section and item 22) if incremental re-encryption of only changed files becomes a goal, though a first cut needs neither - one plaintext file to one `.pqf` file, re-encrypted whole on change, is already a complete and useful v1. Filename confidentiality is an open design question worth deciding up front: mirroring plaintext filenames leaks directory structure and names to the storage backend, while encrypting them (as gocryptfs does) requires a deterministic, collision-resistant filename scheme that hasn't been designed here yet.

### Constant-time test harness extension *(complete)*

`pqfile/examples/ct_shamir.rs` (Shamir GF(256) reconstruction), `ct_decrypt.rs` (decryption error path: tamper-position timing), and `ct_passphrase.rs` (wrong-passphrase rejection: unrelated vs near-miss guess) are standalone dudect-style Welch t-test binaries. All three require a quiet machine and ≥100 000 samples for a meaningful verdict; they are deliberately not run in CI.

## Evaluated and not planned

Considered during the 2026-07-08 ecosystem review and deliberately left off the roadmap, recorded so they are not re-litigated from scratch:

- **Ascon-AEAD128 (NIST SP 800-232)**: standardized in 2025 for constrained devices, but it is slower than ChaCha20-Poly1305 on every platform pqfile targets (desktop, server, WASM), and the Rust crate is unaudited. No fit unless an embedded target appears.
- **Miri /** `cargo-careful` **CI jobs**: `#![deny(unsafe_code)]` at the crate root leaves almost no first-party unsafe surface (one sanctioned mmap call), and dependency unsafe is better covered by the existing fuzzing plus `cargo vet`. Poor signal per CI minute.
- **io_uring async I/O (**`tokio-uring` **/** `compio`**)**: encryption throughput is CPU-bound on the AEAD and KDF paths, not syscall-bound; the Linux-only complexity is not justified by the profile.
- `memsecurity` **/ ASCON-encrypted in-RAM secrets**: encrypting secrets in memory with a key that lives in the same address space adds obfuscation, not a security boundary. The `memsec` mlock approach (shipped 2026-07-08 as `pqfile/src/secret.rs`) addresses the actual threat, which is swap and crash dumps.

Considered during the 2026-07-13 review and deliberately left off the roadmap:

- **Physical side-channel (power/EM) countermeasures for ML-KEM/ML-DSA**: 2026 research (e.g. eprint 2026/056, the PROACT2025 survey) demonstrated real power/EM attacks against unprotected ML-KEM and ML-DSA implementations, including full ML-KEM key recovery in minutes. These attacks require an adversary with physical instrumented access to the running device (a probe on the chip or its power rail) - a threat model that smartcards and embedded secure elements must defend against, but that a CLI/GUI/WASM application running on a general-purpose desktop or server OS does not claim to. Masking countermeasures at that level are out of scope here. This is a distinct concern from the *local/remote timing* side-channels pqfile already defends against via the `ct_`* dudect harnesses (item stays in scope); it is specifically about physical instrumentation, which is a different attacker.
- **FIPS 140-3 cryptographic module validation**: pqfile builds on RustCrypto's pure-software `ml-kem`/`ml-dsa`/AEAD implementations (plus the optional `libcrux-ml-kem` backend), none of which is an independently validated FIPS 140-3 module. Formal CMVP validation is a multi-year, six-figure-plus process scoped to a specific module boundary and build, and would need to be redone on every dependency bump - not a fit for an actively-developed OSS crate. Noted for awareness given Executive Order 14412 (June 2026) sets a 2031 deadline for US federal high-value systems to move to post-quantum signatures, but pqfile is not pursuing federal-procurement compliance as a goal.

## Security invariants

The following properties are invariants, not roadmap items. Any proposal that weakens them requires explicit justification and a major version bump:

- All cryptographic operations run locally. No data is sent to a server.
- The entire `.pqf` file (header + payload) is authenticated before any plaintext is returned.
- Secret material is zeroized from memory on drop.
- Each encryption produces a fresh KEM ciphertext and a fresh random nonce.
- In hybrid mode, each encryption also produces a fresh ephemeral X25519 scalar.
